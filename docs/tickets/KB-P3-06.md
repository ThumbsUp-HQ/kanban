### User Story
As a **project member**, I need **to subscribe to issues (automatically when I create, am assigned, or am mentioned with access), mute individual event types, and read my notifications** so that **I receive relevant updates only for issues I can still see, delivered through the transactional outbox**.

**Requirement Traceability:** Spec S7.2 `8l`; S2.2/S2.4 (`outbox_events`, `RealtimeBroker`); requirement `#8l` | **Dependencies:** `KB-P3-05`, `KB-P3-03`, `KB-P1-18`

### Scoped Technical Actions
1. **Target Files:** `kanban/api/v1/subscriptions.py`, `kanban/api/v1/notifications.py`, `kanban/api/v1/schemas/notifications.py`, `kanban/services/subscriptions.py`, `kanban/services/notifications.py` (activity listener), `database/migrations/versions/<rev>_notifications.py`.
2. **Migration:**
   ```sql
   ALTER TABLE issue_subscriptions ADD COLUMN IF NOT EXISTS muted_event_types TEXT[] NOT NULL DEFAULT '{}';
   CREATE TABLE notifications (
     id                     UUID PRIMARY KEY DEFAULT uuidv7(),
     workspace_id           UUID NOT NULL,
     recipient_principal_id UUID NOT NULL REFERENCES principals(id),
     issue_id               UUID NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
     activity_record_id     UUID NOT NULL,
     event_type             TEXT NOT NULL,
     created_at             TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
     read_at                TIMESTAMPTZ,
     UNIQUE (recipient_principal_id, activity_record_id)
   );
   CREATE INDEX notifications_unread ON notifications (recipient_principal_id, created_at DESC) WHERE read_at IS NULL;
   ```
   `ENABLE` + `FORCE ROW LEVEL SECURITY`; policy `recipient_principal_id = current_setting('app.principal_id')::uuid` for `SELECT`/`UPDATE`; `INSERT` permitted for the app role within the issue's workspace.
3. **Endpoints:**

   | Method + Path | Capability | Success | Errors |
   | :-- | :-- | :-- | :-- |
   | `GET /api/v1/issues/{issue_ref}/subscription` | `VIEW` | `200 {"subscribed": bool, "muted_event_types": [], "source": "manual|creator|assignee|mention|null"}` | `404` |
   | `PUT /api/v1/issues/{issue_ref}/subscription` | `VIEW` | `200` (idempotent) | `404` |
   | `PATCH /api/v1/issues/{issue_ref}/subscription` body `{"muted_event_types": ["ISSUE_FIELD_CHANGED"]}` | `VIEW` + subscribed | `200` | `404`, `409 NOT_SUBSCRIBED`, `422 EVENT_TYPE_NOT_MUTABLE` |
   | `DELETE /api/v1/issues/{issue_ref}/subscription` | `VIEW` | `204` (idempotent) | `404` |
   | `GET /api/v1/notifications?unread=true&cursor=&limit=` | self | `200` | `422` |
   | `POST /api/v1/notifications/{id}/read` | self | `204` | `404` (other user's id) |
   | `POST /api/v1/notifications/read-all` | self | `200 {"marked": n}` | - |

   - Mutable event types allowlist: `COMMENT_CREATED`, `ISSUE_STATE_CHANGED`, `ISSUE_FIELD_CHANGED`, `ISSUE_DESCRIPTION_CHANGED`, `ISSUE_LABELS_CHANGED`, `ASSIGNEE_ADDED`, `ASSIGNEE_REMOVED`; max `7` entries, unique.
   - Notification item: `{"id", "issue": {"key": "KAN-142", "summary": "..."}, "event_type": "COMMENT_CREATED", "actor": {"handle": "maya"} | {"redacted": true, "label": "1 External Collaborator"}, "created_at", "read_at": null}`. `limit` `1..100` default `30`, keyset cursor on `(created_at, id)`.
4. **Auto-subscribe rules (registered via `register_activity_listener` from KB-P3-01a):** on `ISSUE_CREATED` subscribe the creator (`source=creator`); on `ASSIGNEE_ADDED` with `kind=principal` subscribe that principal if they hold `VIEW` (`source=assignee`); on `COMMENT_CREATED` subscribe each `mentioned_principal_ids` member holding `VIEW` (`source=mention`). Free-text assignees and unacknowledged/no-access mentions are never subscribed. An explicit `DELETE` (unsubscribe) is remembered (`issue_subscriptions` row with `unsubscribed_at` or equivalent tombstone) so auto rules do not re-subscribe the same principal.
5. **Delivery:** for each issue activity, for each subscriber where `subscriber != actor`, `event_type` not muted, and subscriber currently holds `VIEW` on the issue (checked in the same transaction against `effective_resource_access`), insert one `notifications` row and one `outbox_events` row `{"topic": "notification.created", "recipient_principal_id", "notification_id"}` (KB-P1-18). Outbox payload carries ids only, never issue text. Max `500` recipients per activity; above that, log a structured warning and deliver to the first `500` by subscription age (bounded transaction).
6. **Activity events emitted:** none. Subscribe/unsubscribe/mute are personal preferences and are not written to the hash-chained ledger (documented).

### Mandatory Feature Unit Tests
- **Test File(s):** `kanban/tests/api/test_subscriptions.py`, `kanban/tests/services/test_notifications.py`
- **Required Test Cases:**
  1. Positive: creator auto-subscribed with `source=creator`; another user's comment creates exactly one notification for the creator and one `outbox_events` row with topic `notification.created`.
  2. Security: subscriber whose `VIEW` is revoked (explicit `DENY`) receives no notification for the next event; free-text assignee produces no subscription; `POST /api/v1/notifications/{id}/read` on another user's notification returns `404`.
  3. Mute: muting `COMMENT_CREATED` suppresses comment notifications but not `ISSUE_STATE_CHANGED`; muting `PROJECT_CREATED` returns `422 EVENT_TYPE_NOT_MUTABLE`.
  4. Actor exclusion and tombstone: actor never notifies self; after explicit unsubscribe, being newly assigned does not re-subscribe.
  5. Boundary: 501 subscribers yields exactly 500 notifications; `limit=101` returns `422`; `read-all` returns correct `marked` count.
  6. Outbox payload contains no `summary` or `body` keys.
- Clean-DB `SAVEPOINT` harness; one `@pytest.mark.committed_db` test asserting `pg_notify('outbox_wakeup')` fires. Coverage `>= 95%`.
