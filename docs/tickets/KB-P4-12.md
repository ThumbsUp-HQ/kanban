### User Story
As a **Server or Project Admin invoking destructive operations through an admin agent**, I need **a mandatory two-stage `destructive_lifecycle` gate (`request_delete` -> `execute_delete`) where Stage 1 computes the exact recursive blast radius and mints a 5-minute single-use token cryptographically bound to `(caller_id, target_uuid, mode, blast_hash)`, and Stage 2 executes soft-trash or audited permanent purge only when `confirmation_token`, `confirm_phrase`, and live `blast_hash` all match** so that **no single hallucinated MCP tool call can ever destroy issues, docs, cycles, modules, views, or projects**.

**Requirement Traceability:** Spec S11.4 tool 12 (`destructive_lifecycle`: `request_delete` -> `execute_delete`, 5-minute single-use `confirmation_token` bound to `(caller_id, target_uuid, blast_hash)`, `confirm_phrase`, soft-trash vs permanent purge); S7.2 `8q` (blast radius); S12.3 (zero silent cascade link drops); requirements `#8q`, `#12`, `#13j` | **Dependencies:** `KB-P4-09a`, `KB-P3-09b`, `KB-P3-14`, `KB-P3-15`, `KB-P3-10a`, `KB-P3-10b`, `KB-P3-11`

### Scoped Technical Actions
1. **Target Files:** `database/migrations/versions/<rev>_destructive_confirmation_tokens.py`, `database/models/destructive_token.py`, `kanban/services/destructive_lifecycle.py`, `kanban/api/v1/admin/destructive.py` (`POST /api/v1/admin/destructive:request`, `POST /api/v1/admin/destructive:execute`), `mcp/surfaces/admin/destructive_lifecycle.py`, `mcp/surfaces/admin/__init__.py` (register tool 12), `mcp/auth.py` (`destructive_lifecycle` -> `admin:destructive`).
2. **DDL `destructive_confirmation_tokens` (`FORCE RLS` workspace policy):**
   ```sql
   CREATE TABLE destructive_confirmation_tokens (
       id                    UUID PRIMARY KEY DEFAULT uuidv7(),
       workspace_id          UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
       token_sha256          BYTEA NOT NULL UNIQUE CHECK (octet_length(token_sha256) = 32),
       caller_principal_id   UUID NOT NULL REFERENCES principals(id) ON DELETE CASCADE,
       target_object_id      UUID NOT NULL,
       target_object_type    object_kind NOT NULL,
       mode                  TEXT NOT NULL CHECK (mode IN ('trash', 'permanent_purge', 'restore')),
       blast_hash            TEXT NOT NULL CHECK (char_length(blast_hash) = 64),
       confirm_phrase        TEXT NOT NULL,
       blast_summary_json    JSONB NOT NULL,
       created_at            TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
       expires_at            TIMESTAMPTZ NOT NULL,
       consumed_at           TIMESTAMPTZ,
       CHECK (expires_at <= created_at + interval '300 seconds'),
       FOREIGN KEY (target_object_id, target_object_type) REFERENCES objects (id, object_type) ON DELETE CASCADE
   );
   ```
   Plaintext token format: `kb_del_<base64url(os.urandom(32)) without padding>`; returned once by `request_delete`, stored solely as `sha256(plaintext)`, redacted as `"***"` by `mcp/yaml_out.py` transcript logging if echoed in test fixtures (with a dedicated test verifying the raw token works across Stage 1 -> Stage 2).
3. **Recursive Blast-Radius & Execution Engine (`kanban/services/destructive_lifecycle.py`):**
   - Supported `target_kind` values: `issue`, `project`, `doc`, `page`, `sticky`, `cycle`, `module`, `view`.
   - Authorization:
     - All calls require `admin:destructive` MCP scope + caller `AAL2` (`403 AAL2_REQUIRED`).
     - `mode="trash"` or `mode="restore"`: caller must hold `DELETE` capability on the target object (or `PROJECT_ADMIN` / `SERVER_ADMIN`); unreadable target -> equalized `404`.
     - `mode="permanent_purge"`: restricted strictly to `SERVER_ADMIN` (`403 SERVER_ADMIN_REQUIRED` otherwise), and target must already sit in soft-trash (`objects.deleted_at IS NOT NULL`) for `issue`, `project`, `doc`, `page`, `sticky` (`409 SOFT_TRASH_REQUIRED_FIRST`), whereas `cycle`, `module`, and `view` (which have no soft-trash state in `KB-P3-10a/b` / `KB-P3-11`) support `permanent_purge` directly after link-audit accounting.
   - `compute_object_blast_radius(session, target_obj, mode) -> ObjectBlastRadius`:
     - Delegates `issue` to `compute_blast_radius` (`KB-P3-09b`) and generalizes across `project` (counts issues, docs, pages, stickies, cycles, modules, views, inbound/outbound cross-project `object_links`), `doc`/`page` (descendant `ltree` pages, `page_versions`, inbound/outbound links), `sticky`, `cycle` (assigned issues to clear), `module` (assigned issues + defaults to clear), and `view`.
     - `blast_hash` = lowercase SHA-256 hex of canonical JSON `{target_object_id, target_object_type, mode, content_etag_or_updated_at, sorted_descendant_ids, sorted_inbound_link_ids, sorted_outbound_link_ids, child_counts}`.
     - `required_confirm_phrase` = `f"{'TRASH' if mode == 'trash' else ('RESTORE' if mode == 'restore' else 'PURGE')} {target_object_type.upper()} {canonical_key}"` (e.g., `"TRASH ISSUE KAN-142"`, `"PURGE PROJECT KAN"`).
   - **Stage 2 (`execute_delete`) Zero-TOCTOU Verification:**
     1. Atomically claim token: `UPDATE destructive_confirmation_tokens SET consumed_at = clock_timestamp() WHERE token_sha256 = :digest AND consumed_at IS NULL AND expires_at > clock_timestamp() RETURNING *`. If `0` rows: distinguish expired vs already-consumed vs unknown only as `409 CONFIRMATION_TOKEN_INVALID_OR_EXPIRED` (single constant-time lookup).
     2. Verify `row.caller_principal_id == current_principal_id` (`403 TOKEN_CALLER_MISMATCH`), `row.target_object_id == resolved_target_id`, `row.mode == mode` (`409 TOKEN_TARGET_MISMATCH`), and `confirm_phrase == row.confirm_phrase` (`422 CONFIRM_PHRASE_MISMATCH` - note: on phrase or caller mismatch, rollback transaction so an honest typo does not burn the token, OR keep consumed? Consume on security mismatch (`caller`/`target`), allow retry or require fresh `request_delete` - **fail closed: commit consumption or reject before claim**: validate `confirm_phrase` and `(caller, target, mode)` inside the `WHERE` / before commit; any mismatch marks `consumed_at` in an autonomous write or rejects and forces minting a fresh token so attackers cannot brute-force phrases!). Specifically: burn the token on ANY failed `execute_delete` attempt (`consumed_at` committed) and return `CONFIRM_PHRASE_MISMATCH` / `TOKEN_CALLER_MISMATCH`.
     3. Lock target row `SELECT ... FOR UPDATE`, recompute `live_blast_hash`; if `live_blast_hash != row.blast_hash` -> `412 BLAST_RADIUS_CHANGED` with fresh counts (zero destructive writes).
     4. For `permanent_purge`, first run `audit_object_links(workspace_id)` + `purge_invalid_object_links(audit_ids, caller_id, reason)` (`KB-P1-15`/`16`) so `ON DELETE RESTRICT` on `object_links` is satisfied with full audit provenance (never bypassing link ledger!), then delete dependent rows and `objects` spine row, recording `DESTRUCTIVE_LIFECYCLE_EXECUTED` in `activity_records`.
4. **MCP Tool 12 (`mcp/surfaces/admin/destructive_lifecycle.py`):**
   - Input schema (`additionalProperties: false`):
     ```yaml
     action: {enum: [request_delete, execute_delete, restore, help]} # required
     target_kind: {enum: [issue, project, doc, page, sticky, cycle, module, view]} # required except help
     target: {type: string}              # human key or uuid; required except help
     mode: {enum: [trash, permanent_purge], default: trash}
     confirmation_token: {type: string}  # required for execute_delete
     confirm_phrase: {type: string}      # required for execute_delete
     reason: {type: string, minLength: 10, maxLength: 500} # required for execute_delete and restore
     ```
   - `summary` YAML for `request_delete`:
     ```yaml
     stage: confirmation_required
     target: KAN-142
     mode: trash
     blast_summary: "2 sub-issues unparented, 3 inbound object_links flagged"
     blast_hash: 5e1c...
     confirm_phrase: "TRASH ISSUE KAN-142"
     confirmation_token: kb_del_...
     expires_in_sec: 300
     ```
5. **Error codes appended (`mcp/errors.py`):** `CONFIRMATION_TOKEN_INVALID_OR_EXPIRED`, `TOKEN_CALLER_MISMATCH`, `TOKEN_TARGET_MISMATCH`, `BLAST_RADIUS_CHANGED`, `SOFT_TRASH_REQUIRED_FIRST`, `SERVER_ADMIN_REQUIRED`.

### Mandatory Feature Unit Tests
- **Test File(s):** `kanban/tests/api/test_destructive_lifecycle.py`, `mcp/tests/admin/test_destructive_lifecycle.py`
- **Required Test Cases:**
  1. Positive two-stage flows: (a) `request_delete(issue="KAN-142", mode="trash")` -> `execute_delete` moves `KAN-142` to trash (`deleted_at` set, sub-issues unparented) -> `restore` brings it back; (b) trash `KAN-142`, then as `SERVER_ADMIN` run `request_delete(mode="permanent_purge")` -> `execute_delete` purges flagged links via `purge_invalid_object_links` (`INVALID_OBJECT_LINK_PURGED` + `DESTRUCTIVE_LIFECYCLE_EXECUTED` rows present) and removes `KAN-142`; (c) two-stage delete of a `page` subtree and a `module`.
  2. Replay, expiry & binding security: replaying the same `confirmation_token` a second time returns `CONFIRMATION_TOKEN_INVALID_OR_EXPIRED`; advancing clock `301s` expires the token; Admin B attempting to execute a token minted by Admin A returns `TOKEN_CALLER_MISMATCH` and burns the token; swapping `target` from `KAN-142` to `KAN-143` returns `TOKEN_TARGET_MISMATCH`; wrong `confirm_phrase` (`"DELETE KAN-142"`) returns `CONFIRM_PHRASE_MISMATCH` and burns the token.
  3. Blast-hash TOCTOU protection: after `request_delete` on `KAN-142`, attach a new `BLOCKS` link or child issue `KAN-199`; `execute_delete` returns `BLAST_RADIUS_CHANGED` (`412`) and leaves `KAN-142` untouched.
  4. Role & scope gates: `admin:write` key (without `admin:destructive`) -> `INSUFFICIENT_SCOPE`; `PROJECT_ADMIN` (not `SERVER_ADMIN`) requesting `permanent_purge` -> `SERVER_ADMIN_REQUIRED`; `permanent_purge` on an active non-trashed issue -> `SOFT_TRASH_REQUIRED_FIRST`; AAL1 token -> `AAL2_REQUIRED`.
