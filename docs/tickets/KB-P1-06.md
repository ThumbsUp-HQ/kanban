### User Story
As a **project member organizing work into sub-issues**, I need **a database trigger that locks the ancestor chain, rejects parent cycles, caps nesting at depth 6, and rewrites `ancestry_path` for the moved issue and all of its descendants** so that **the parent hierarchy is always an acyclic tree with correct materialized paths, even under concurrent reparenting**.

**Requirement Traceability:** `S7.2 8h` (`parent_issue_id` + `ancestry_path ltree`, `max_depth <= 6`, `FOR UPDATE` ancestor locks, reject `A -> B -> A`), Requirement `#8h` | **Dependencies:** `KB-P1-05`

### Scoped Technical Actions
1. **Target Files:**
   - `database/migrations/versions/p1_06_parent_dag.py`
   - `database/migrations/sql/p1_06_parent_dag.up.sql`, `database/migrations/sql/p1_06_parent_dag.down.sql`
2. **Schema additions:**
   ```sql
   CREATE INDEX issues_ancestry_gist ON issues USING gist (ancestry_path);
   ALTER TABLE issues ADD CONSTRAINT issues_ancestry_depth_chk CHECK (nlevel(ancestry_path) BETWEEN 1 AND 6);
   CREATE FUNCTION issue_ltree_label(p_id uuid) RETURNS ltree LANGUAGE sql IMMUTABLE PARALLEL SAFE
     AS $$ SELECT text2ltree(replace(p_id::text, '-', '')) $$;
   ```
   Depth definition: a root issue has `nlevel(ancestry_path) = 1`; the deepest allowed descendant has `nlevel = 6`.
3. **`issues_parent_dag_biu` (BEFORE INSERT OR UPDATE OF parent_issue_id ON issues FOR EACH ROW)** - replaces the simple path logic of KB-P1-05 for the parent case:
   1. `NEW.parent_issue_id IS NULL` -> `NEW.ancestry_path := issue_ltree_label(NEW.id)`; return.
   2. `NEW.parent_issue_id = NEW.id` -> `PARENT_SELF_REFERENCE`.
   3. Lock ancestors top-down to avoid lock-order inversion:
      ```sql
      SELECT ancestry_path INTO v_parent_path FROM issues WHERE id = NEW.parent_issue_id;
      PERFORM 1 FROM issues WHERE ancestry_path @> v_parent_path
        ORDER BY nlevel(ancestry_path) FOR UPDATE;
      ```
      Missing parent -> `PARENT_NOT_FOUND`.
   4. Parent in a different project -> `PARENT_CROSS_PROJECT`.
   5. Cycle: `v_parent_path ~ ('*.' || replace(NEW.id::text,'-','') || '.*')::lquery` -> `PARENT_CYCLE`.
   6. Depth: `nlevel(v_parent_path) + 1 + v_subtree_height > 6` where `v_subtree_height = COALESCE(max(nlevel(d.ancestry_path)) - nlevel(OLD.ancestry_path), 0)` over descendants `d.ancestry_path <@ OLD.ancestry_path` (0 on INSERT) -> `PARENT_MAX_DEPTH_EXCEEDED`.
   7. `NEW.ancestry_path := v_parent_path || issue_ltree_label(NEW.id)`.
4. **`issues_parent_dag_au` (AFTER UPDATE OF parent_issue_id, WHEN `OLD.ancestry_path IS DISTINCT FROM NEW.ancestry_path`):**
   ```sql
   UPDATE issues SET ancestry_path = NEW.ancestry_path || subpath(ancestry_path, nlevel(OLD.ancestry_path))
    WHERE ancestry_path <@ OLD.ancestry_path AND id <> NEW.id;
   ```
   This statement updates only `ancestry_path`, so `BEFORE ... OF parent_issue_id` does not re-fire.
5. **Parent deletion:** the existing `ON DELETE SET NULL` FK action issues `UPDATE ... SET parent_issue_id = NULL` on children, which fires both triggers; children become roots and their subtrees are rebased. No extra code beyond tests.
6. Concurrent opposite moves (`A under B` and `B under A`) may raise `40P01 deadlock_detected` in one transaction; this is acceptable (no cycle can commit) and documented in a `COMMENT ON TRIGGER`.
7. **Down migration:** drops both triggers, `issue_ltree_label`, `issues_ancestry_depth_chk`, `issues_ancestry_gist`, and restores the KB-P1-05 path logic (re-create the `issues_validate_biu` function body from KB-P1-05 if it was replaced).

### Mandatory Feature Unit Tests
- **Test File(s):** `database/tests/test_p1_06_parent_dag.py`, `database/tests/test_p1_06_parent_concurrency.py`, `database/tests/migrations/test_p1_06_migration.py`
- **Required Test Cases:**
  1. Positive: A (root) <- B <- C; `C.ancestry_path = label(A).label(B).label(C)`, `nlevel = 3`.
  2. Positive (subtree move): with A<-B<-C and root X, `UPDATE issues SET parent_issue_id = X WHERE id = B` -> `B.path = X.B`, `C.path = X.B.C`; A has no descendants.
  3. Negative (cycle): A<-B; `UPDATE A SET parent_issue_id = B` raises `PARENT_CYCLE`; self-parent raises `PARENT_SELF_REFERENCE`.
  4. Negative (depth): chain of 6 levels accepted; inserting a 7th-level child raises `PARENT_MAX_DEPTH_EXCEEDED`; moving a 3-level subtree under a level-4 node raises `PARENT_MAX_DEPTH_EXCEEDED`.
  5. Negative/security: parent in another project raises `PARENT_CROSS_PROJECT`; nonexistent parent raises `PARENT_NOT_FOUND` (FK `23503` is also acceptable if raised first; test asserts one of the two).
  6. Boundary (parent delete path): after `UPDATE issues SET parent_issue_id = NULL WHERE id = B` (simulating the SET NULL action), B becomes root with `nlevel = 1` and C is rebased to `B.C`.
  7. Concurrency (`@pytest.mark.committed_db`): two connections concurrently set `A.parent = B` and `B.parent = A`; exactly one commits; the other fails with `PARENT_CYCLE` or `40P01`; afterwards no row has its own label inside its parent's path.
  8. Migration up/down: upgrade `p1_06_parent_dag` -> triggers + `issues_ancestry_gist` exist; downgrade to `previous_of(...)` -> absent; re-upgrade succeeds.
  - Non-concurrency tests run under the KB-P0-05 clean-DB `SAVEPOINT` harness; touched-module coverage `>= 95%`.
