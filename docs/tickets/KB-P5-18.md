### User Story
As a **workflow owner relying on AI/CLI transition gates**, I need **the two-phase async gate coordinator that holds a transition in `pending_async` (`202`), commits only after every agent hook approves and the issue body hash still matches the snapshot, and snaps back with a `🛑🤖` comment on reject/timeout** so that **a slow or hostile agent can never freeze the UI, approve a stale ticket (zero TOCTOU), loop transitions beyond `hop_depth 3`, or silently pass when it fails**.

**Requirement Traceability:** `S14.1` (sequence steps `202 Accepted`, `⏳🤖`, approve commit `✅🤖`, reject snap-back + `🛑🤖` comment), `S14.2` (`status` enum, `hop_depth <= 3`, `issue_body_sha256_snapshot`, `failure_policy`, `pending_transition_exec_id`), `S14.3` item 3 last bullet (`issues.description_sha256 == issue_body_sha256_snapshot`), `S11.2` item 6 (`status: pending_agent_gate`, `execution_id`, `active_agent`), `S1.3` item 2 | ScriptRunner row of the traceability matrix | **Dependencies:** `KB-P5-17a`, `KB-P4-06`

### Scoped Technical Actions
1. **Target Files:**
   - `kanban/workflows/async_gate.py` (`AgentGateDispatcher` implements `AsyncGateDispatcher`; `GateCoordinator`)
   - `kanban/workflows/gate_types.py` (`GateDecision` frozen dataclass, `GateEventType` enum)
   - `kanban/workflows/gate_sweeper.py` (`GateTimeoutSweeper.run_once(now)`)
   - `kanban/api/v1/transitions.py` (edit: `202` path + `DELETE /api/v1/transitions/{execution_id}` cancel)
   - `kanban/issues/serializers.py` (edit: add `pending_gate`, `latest_gate_verdict`)
   - `mcp/agent/tools/transition_ticket.py` (edit: replace the `KB-P4-06` stub with real `pending_agent_gate` mapping)
2. **Dispatch (`AgentGateDispatcher.dispatch(execution, agent_hooks)`):** in the engine transaction: set execution `status='pending_async'`, `issues.pending_transition_exec_id = execution.id`, insert `workflow_hook_invocations` row `status='running'` for the FIRST agent hook only (hooks run sequentially in `sort_rank` order), insert outbox event `workflow.gate.dispatch` `{execution_id, hook_id, agent_definition_id, deadline_at}` where `deadline_at = now + agent_definitions.timeout_ms`. Return `202 {status: "pending_agent_gate", execution_id, active_agent: <slug>, hook_name, harness_kind}`. The state is NOT changed.
3. **`GateDecision`:** `decision: Literal["approve","reject"]`, `reason_markdown: str`, `field_updates: Mapping[str, JSONValue]`, `add_labels: tuple[str, ...]`, `add_links: tuple[LinkSpec, ...]`, `verdict_sha256: bytes` (32 bytes), `latency_ms: int`. Validation of raw agent output into `GateDecision` is owned by `KB-P5-19a`; this ticket trusts only the dataclass type and re-checks `field_updates` keys against `hook.allowed_mutable_fields`.
4. **`GateCoordinator.record_decision(execution_id, hook_id, decision)`** (single transaction, `SELECT ... FOR UPDATE` on execution and issue):
   - Reject if execution not `pending_async` or `hook_id` is not the currently `running` invocation -> `GATE_DECISION_OUT_OF_ORDER` (idempotent no-op for duplicate identical `verdict_sha256`).
   - `approve` and more agent hooks remain -> mark invocation `allowed`, open next invocation, emit next `workflow.gate.dispatch`.
   - `approve` on the last hook -> verify `issues.description_sha256 = execution.issue_body_sha256_snapshot` AND `issues.state_id = execution.from_state_id`; on mismatch -> execution `cancelled`, clear hold, activity `GATE_ABORTED_STALE`, event `workflow.gate.cancelled` (reason `STALE_SNAPSHOT`); on match -> apply accumulated `field_updates` via `apply_field_updates` (KB-P5-17a), labels, links, set `state_id` (with `app.transition_exec_id`), execution `approved`, `verdict_json`, `completed_at`, clear hold, activity `GATE_APPROVED` with `verdict_sha256` hex + latency, event `workflow.gate.approved`.
   - `reject` -> execution `rejected`, clear hold (state never changed, so "snap back" is a client concern), post comment authored by the agent's `principal_id`: ``🛑🤖 Gate `<hook_name>` (<harness label>) vetoed <from> -> <to>`` + blank line + `reason_markdown` passed through the `KB-P2-13` normalizer and `KB-P2-17` scrubber, capped `16,384` bytes; activity `GATE_REJECTED`; event `workflow.gate.rejected`.
5. **Failures and timeouts (`GateTimeoutSweeper.run_once(now)` + `GateCoordinator.record_failure(execution_id, hook_id, code)`):** sweeper selects `pending_async` executions whose running invocation exceeded `deadline_at` (`FOR UPDATE SKIP LOCKED`, batch `<= 100`). `failure_policy='fail_closed'` -> treat as reject with comment reason `Gate timed out after <timeout_ms> ms` (status `timed_out`) or `Gate failed: <code>` (status `rejected`); `fail_open_warn` -> invocation `timed_out|error`, activity `GATE_FAIL_OPEN_WARN`, continue to next hook or commit (still subject to the TOCTOU check).
6. **Cancel:** `DELETE /api/v1/transitions/{execution_id}` allowed for the invoking principal or a `PROJECT_ADMIN`; sets `cancelled`, clears hold, event `workflow.gate.cancelled`; others -> `404`.
7. **Hop depth:** engine-originated nested transitions from gate side effects pass `parent_execution_id`; `hop_depth > 3` already rejected by `KB-P5-17a`; this ticket adds a test that a gate approval which triggers a follow-up automation chain stops at depth `3`.
8. **Realtime events (outbox via `KB-P1-18`, fanned out with per-recipient RLS filtering by `KB-P3-16`):** types `workflow.gate.pending|approved|rejected|timed_out|cancelled`; payload `{issue_id, issue_key, execution_id, hook_name, agent_slug, harness_kind, harness_label, from_state, to_state, started_at, completed_at?, latency_ms?, verdict_sha256?, reason_preview?}` where `reason_preview` is the first 2 lines, `<= 280` chars, scrubbed. No raw `verdict_json` in events.
9. **Serializer fields:** `pending_gate: {execution_id, hook_name, agent_slug, harness_label, started_at, deadline_at} | null`; `latest_gate_verdict: {decision, hook_name, completed_at, latency_ms, verdict_sha256} | null`.
10. **MCP:** `transition_ticket` returns `status: pending_agent_gate`, `execution_id`, `active_agent` on `202`; maps `409 TRANSITION_PENDING` to a structured error.

- **Required Test Cases:**
  1. Positive: 1 agent hook -> `202` with `execution_id`, `active_agent`; issue `pending_transition_exec_id` set, state unchanged; approve -> state = `to_state`, `✅` activity with `verdict_sha256`, event `workflow.gate.approved`.
  2. Positive: 2 agent hooks -> sequential dispatch; second dispatched only after first approves; reject on second -> state unchanged, `🛑🤖` comment by agent principal.
  3. Security / TOCTOU: description edited after `202` -> approve -> `cancelled`, `GATE_ABORTED_STALE`, state unchanged.
  4. Security: `field_updates={"state":"Done"}` or a key outside `allowed_mutable_fields` -> rejected with `HOOK_MUTATION_NOT_ALLOWED`, treated per `failure_policy`; reason containing `<script>` and `sk-live-...` is sanitized and scrubbed in the comment and in `reason_preview`.
  5. Security: decision for a non-running hook -> `GATE_DECISION_OUT_OF_ORDER`; replay of identical decision -> no duplicate comment/activity.
  6. Boundary: sweeper at `deadline_at + 1ms` -> `fail_closed` -> `timed_out` + comment; `fail_open_warn` -> continue + `GATE_FAIL_OPEN_WARN`; malformed cassette -> failure path.
  7. Boundary: second transition request during `pending_async` -> `409 TRANSITION_PENDING`; cancel by non-invoker member -> `404`; cancel by invoker -> `cancelled` event.
  8. Events: each terminal path emits exactly 1 outbox event of the correct type; payload has no `verdict_json` key.
  9. MCP: `transition_ticket` on gated transition returns `status: pending_agent_gate` with both ids.
