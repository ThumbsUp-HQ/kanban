### User Story
As a **Server/Workspace/Project Administrator or individual engineer configuring bots (`meatloaf-bot`, CI runners, repo-local IDE agents)**, I need **scopable MCP API keys across `global`, `workspace`, and `project` tiers with both `service_bot` and `personal_user` ownership plus per-key `capability_mask`, `allowed_tools`, and `allowed_cidrs` narrowing** so that **cross-workspace bots can operate cleanly without custom wrapper scripts while project/user tokens and bot principals remain strictly least-privilege.**

**Requirement Traceability:** `S11.1` (Hierarchical Scopable Keys: Global, Per-Workspace, Per-Project, Per-User + capability/tool narrowing), `S3.2` (OBO & autonomous service-agent intersection `PrincipalPerms ∩ KeyScope`), requirement `#1`, `#12` | **Dependencies:** `KB-P4-02a`, `KB-P2-11`, `KB-P2-05a`

### Scoped Technical Actions
1. **Target Files:**
   - `database/migrations/versions/<rev>_mcp_scopable_keys.py` - schema upgrade & RLS update on `mcp_api_keys`.
   - `database/models/mcp_api_key.py` - extend SQLAlchemy model for hierarchical scope tiers, ownership, tool allowlist, and CIDRs.
   - `kanban/security/mcp_keys.py` - extend `mint_mcp_api_key()`, `introspect_subject_token()`, and `evaluate_key_boundary()`.
   - `kanban/api/v1/auth_mcp_keys.py` - user self-service endpoints `POST / GET / DELETE /api/v1/auth/mcp-keys` (`owner_kind = 'personal_user'`).
   - `kanban/api/v1/admin/mcp_keys.py` - extend admin endpoints `POST / GET / DELETE /api/v1/admin/mcp-keys` (`owner_kind = 'service_bot'` across `project`, `workspace`, and `global` tiers).
   - `mcp/auth.py` - enforce `capability_mask`, `allowed_tools`, `allowed_cidrs`, and `KeyScopeBoundary` on `tools/list` and `tools/call`.
2. **DDL Upgrade (`mcp_api_keys`):**
   - Relax `workspace_id` to nullable **only** when `scope_tier = 'global'` and add strict tier/ownership constraints:
     ```sql
     ALTER TABLE mcp_api_keys
         ALTER COLUMN workspace_id DROP NOT NULL,
         ADD COLUMN scope_tier            TEXT NOT NULL DEFAULT 'workspace'
             CHECK (scope_tier IN ('global', 'workspace', 'project')),
         ADD COLUMN owner_kind            TEXT NOT NULL DEFAULT 'service_bot'
             CHECK (owner_kind IN ('personal_user', 'service_bot')),
         ADD COLUMN project_id            UUID REFERENCES projects(id) ON DELETE CASCADE,
         ADD COLUMN allowed_workspace_ids UUID[],
         ADD COLUMN allowed_project_ids   UUID[],
         ADD COLUMN capability_mask       INTEGER NOT NULL DEFAULT 7 CHECK (capability_mask BETWEEN 1 AND 255),
         ADD COLUMN allowed_tools         TEXT[],
         ADD COLUMN allowed_cidrs         CIDR[],
         ADD CONSTRAINT mcp_keys_tier_shape_chk CHECK (
             (scope_tier = 'global'    AND workspace_id IS NULL AND project_id IS NULL) OR
             (scope_tier = 'workspace' AND workspace_id IS NOT NULL AND project_id IS NULL) OR
             (scope_tier = 'project'   AND workspace_id IS NOT NULL AND project_id IS NOT NULL)
         );
     ```
   - RLS Policy Update: `SERVER_ADMIN` sees `global` keys; `WORKSPACE_ADMIN` sees keys matching `workspace_id`; `PROJECT_ADMIN` sees `project`-tier keys on their `project_id`; any user sees rows where `owner_kind = 'personal_user' AND principal_id = app.principal_id`.
3. **Minting Authorization Matrix:**
   - **`owner_kind = 'service_bot'` (`POST /api/v1/admin/mcp-keys`, always requires `AAL2` -> `403 AAL2_REQUIRED` if `aal_level < 2`):**
     - `scope_tier = 'global'`: requires `SERVER_ADMIN`; binds to an `AGENT` or `SERVICE_PRINCIPAL` (`principal_id`); optional `allowed_workspace_ids` restricts which workspaces the global bot may access (`NULL` = all workspaces where the bot principal holds RBAC/ACL grants).
     - `scope_tier = 'workspace'`: requires `WORKSPACE_ADMIN` on `workspace_id` (or `SERVER_ADMIN`); optional `allowed_project_ids` subset within `workspace_id`.
     - `scope_tier = 'project'`: requires `PROJECT_ADMIN` on `project_id` (or `WORKSPACE_ADMIN` / `SERVER_ADMIN`); sets `allowed_project_ids = ARRAY[project_id]`.
   - **`owner_kind = 'personal_user'` (`POST /api/v1/auth/mcp-keys`):**
     - `principal_id` is locked to `caller.principal_id` (cannot mint personal keys for another user).
     - Standard authenticated session (`AAL1+`) may mint `agent` or `docs` surface keys; minting an `admin` surface key or `DELETE` capability bit requires `AAL2` (`403 AAL2_REQUIRED`).
     - Caller may pick `scope_tier` = `'global'` (across caller's own accessible workspaces), `'workspace'` (must hold `VIEW` in `workspace_id`), or `'project'` (must hold `VIEW` on `project_id`).
4. **Dual Permission Intersection (`Bot/User Principal ∩ Token Scope`):**
   - Introspection returns `{active, principal_id, owner_kind, scope_tier, workspace_id, project_id, allowed_workspace_ids, allowed_project_ids, scopes, capability_mask, allowed_tools, allowed_cidrs}`.
   - If `allowed_cidrs` is non-null and client IP (`X-Forwarded-For` trusted proxy hop from Caddy or peer socket IP) falls outside `allowed_cidrs` -> `403 KEY_CIDR_DENIED`.
   - If `allowed_tools` is non-null: `tools/list` filters out unlisted tools, and `tools/call` on an unlisted tool returns `isError: true`, `code: INSUFFICIENT_SCOPE`.
   - On every `kanban-api` execution (`KB-P2-11`), effective capabilities on target object `R` equal `EffectivePerms(principal_id, R) & Capability(key.capability_mask) & parse_token_scope_mask(key.scopes)`, and `R.workspace_id` / `R.project_id` must satisfy `KeyScopeBoundary` (else indistinguishable `404` on reads or `403 KEY_SCOPE_VIOLATION` when explicitly targeting an out-of-scope workspace/project).

### Mandatory Feature Unit Tests
- **Test File(s):** `kanban/tests/security/test_mcp_scopable_keys.py`, `mcp/tests/test_key_narrowing.py`
- **Required Test Cases:**
  1. Positive (Global Bot Key - `meatloaf-bot` use case): `SERVER_ADMIN` (`AAL2`) mints a `global` `service_bot` `kb_agt_` key for `meatloaf-bot` principal granted `VIEW|EDIT` in workspaces `ws_a` and `ws_b`, `VIEW`-only in `ws_c`, and `NONE` in `ws_secret`; introspection returns `scope_tier="global"`; `meatloaf-bot` can read/edit in `ws_a`/`ws_b`, can read but gets `403 INSUFFICIENT_CAPABILITY` on write in `ws_c` (bot principal ceiling), and gets `404` on `ws_secret`.
  2. Positive (Per-Project Key): `PROJECT_ADMIN` (`AAL2`) on `KAN` mints a `project`-tier key; key succeeds on `KAN-*` and fails (`403 KEY_SCOPE_VIOLATION` / `404`) when referencing sibling project `NET-*` in the same workspace.
  3. Positive (Per-User Self-Service Key + Live Revocation): standard `MEMBER` (`AAL1`) mints a personal `kb_agt_` key narrowed to `project=KAN`, `capability_mask=VIEW|COMMENT`, `allowed_tools=["search_tickets","read_ticket","add_comment"]`; `tools/list` shows only those 3 tools; `transition_ticket` fails `INSUFFICIENT_SCOPE`; revoking the user's membership in `KAN` immediately causes the personal key to receive `404` on `KAN` without revoking the key row itself.
  4. Security (Privilege Escalation Blocked): `PROJECT_ADMIN` attempting to mint a `workspace` or `global` key -> `403 INSUFFICIENT_CAPABILITY`; `AAL1` user attempting to mint a personal `kb_adm_` key -> `403 AAL2_REQUIRED`; user attempting to view/delete another user's personal key -> `404`.
  5. Security (CIDR Pin & Constraint Checks): key with `allowed_cidrs=["10.8.0.0/16"]` called from `203.0.113.9` -> `403 KEY_CIDR_DENIED`; inserting `scope_tier='global'` with non-null `project_id` raises `23514` (`mcp_keys_tier_shape_chk`).
  6. Migration up/down: upgrade and downgrade cleanly on clean-DB `SAVEPOINT` harness; touched-module coverage `>= 95%`.
